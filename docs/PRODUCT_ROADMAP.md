# Collect 产品化改造方案（C 端视角审查）

> 由产品经理视角审查生成，基线 v2.1.0（versionCode 4）。Expo SDK 58 / RN 0.88，纯 Android，静态内容站 collect.tpgofighting.top，42 篇文章，无后端、无账号、单人维护。

**一句话诊断**：这是一个工程质量远高于产品完成度的产品。同步、离线、App Links、分享接收、签名发布链路都做得很扎实；但"一个陌生人为什么要装它、装完为什么会留下、留下来了怎么不丢数据"这三件事，代码里几乎没有答案。

---

## 一、现状诊断

### 1.1 新用户冷启动与首次体验

| # | 问题 | 严重度 | 依据 |
|---|------|--------|------|
| 1 | **完全没有 onboarding**。路由表里没有任何引导页；新用户装完直接被扔进 42 篇文章的时间线。App 的核心卖点（离线全文、人工精选、无追踪）在首屏一个字都没提，价值感知为零 | **P0** | 路由文件清单 + `(tabs)/index.tsx` 首屏直接渲染列表 |
| 2 | 首屏副标题只有"已收录 42 篇"，这是站长的视角（库存量），不是用户的视角（"这 42 篇为什么值得我读"） | P1 | `(tabs)/index.tsx` line 93 |
| 3 | 新文章的发现依赖用户主动下拉：`newCount` banner 只在 `onRefresh` 后出现，启动自动同步发现的新文章没有 banner，用户感知不到"活着" | P1 | `(tabs)/index.tsx` |
| 4 | 收藏空状态有引导文案，这个做得对；但推荐页、搜索页空状态没有指向下一步动作的引导 | P2 | `recommend.tsx`、`search.tsx` |

### 1.2 核心价值闭环（为什么每天打开）

| # | 问题 | 严重度 | 依据 |
|---|------|--------|------|
| 1 | **没有留存钩子**。时间线按月分组平铺，"已读"只是变灰，没有"继续上次""本周精选""没读完的 3 篇"这类回到 App 的理由 | P1 | `(tabs)/index.tsx` 的 SectionList 结构 |
| 2 | **阅读进度不记忆**。打开即 `markRead(id)`，但没存 scroll 位置，长文重开永远从顶部开始——对"口袋阅读器"这个定位是硬伤 | **P0** | `article/[id].tsx` |
| 3 | 通知是唯一的主动召回手段，但权限申请埋在"我的 → 新文章通知"二级页里，用户不主动翻就永远不会被请求 | **P0** | `src/app/notifications.tsx`、`(tabs)/profile.tsx` |
| 4 | 内容供给节奏完全绑在站长个人效率上：42 篇是存量，App 端所有机制（增量同步、通知）都只是"分发管道"，管道里没水时全白搭 | P1 | PROJECT_ANALYSIS.md §服务端现状 |

### 1.3 账号与数据

现状：全部用户数据（收藏、历史、推荐列表、搜索历史、阅读标记）存在本地 SQLite，设置存 AsyncStorage。**卸载即全部丢失，换机不可迁移。**

**明确建议：现阶段不做账号体系。** 理由：

1. 无后端是硬约束，做账号必然要求服务端（即使只做匿名 device token）；
2. 目标用户量极小，账号系统的开发维护成本远超收益；
3. about 页的卖点文案"无账号 · 无追踪"本身是差异化定位，加账号是自毁定位。

**替代方案：本地优先 + 导出/导入兜底。** 收藏、历史、推荐列表都是纯结构化数据，序列化成 JSON 文件经系统分享面板导出，换机时导入即可。这在纯客户端范围内完全可实现。**导出功能目前完全缺失，这是 P0。**

| # | 问题 | 严重度 |
|---|------|--------|
| 1 | 无导出/导入，换机必丢全部收藏和历史 | **P0** |
| 2 | 无删除应用的任何防呆（没有"你有 12 条收藏，导出一份吗"的提示时机） | P2 |

### 1.4 内容供给的可扩展性

| # | 问题 | 严重度 | 依据 |
|---|------|--------|------|
| 1 | 生产链路是 `extract-data.mjs` 从线上页面抽取 → `deploy-data.sh` rsync，每一篇都要站长手动跑脚本、人工挑选，单篇 8 种 section 结构意味着每篇都是手工结构化编辑，成本极高 | P1 | README §数据来源 |
| 2 | 推荐闭环断裂：用户在 App 里存链接 → 手动复制 → 发给"大肥鱼"→ 站长手动录入。**内部昵称直接暴露给了终端用户** | P1 | `recommend.tsx` |
| 3 | 无内容标签/专栏/系列等组织维度，文章一多时间线平铺就找不到东西 | P2 | `(tabs)/index.tsx` |

**判断**：内容量是产品的第一瓶颈，且只能靠站长解决。App 端能做的是降低"发现存量内容"的成本。真正解法在阶段三的内容工具链，阶段一不要碰。

### 1.5 增长与分发

| # | 问题 | 严重度 | 依据 |
|---|------|--------|------|
| 1 | **分发方式只有 GitHub Release APK 侧载**。目标用户绝大多数不会从 GitHub 下载 APK 并信任未知来源安装提示。这是当前最大的增长断点 | **P0** | README §发布 |
| 2 | 站外落地页断裂：未装 App 的用户点 `/article/<id>` 链接只会落到站点首页，不是文章页——分享出去的内容在 Web 上读不到，裂变链路直接断 | **P0** | CHANGELOG §发布状态 |
| 3 | 分享文案是裸的 `标题\nURL`，没有任何品牌信息；黑白长图卡片是好的开始，但入口埋在阅读页头部第 4 个图标里，用户很难发现 | P1 | `article/[id].tsx` |
| 4 | 应用商店未上架（无软著、无备案材料准备迹象） | P1 | README |

### 1.6 合规与隐私

| # | 问题 | 严重度 | 依据 |
|---|------|--------|------|
| 1 | **无隐私政策页面/链接**。上架国内任何商店都是硬性前置条件 | **P0**（上架前置） | `about.tsx` |
| 2 | 中国 Android 商店上架需要：软件著作权登记（1-2 个月流程，建议立即启动）、ICP 备案（需确认 tpgofighting.top 备案状态）、App 备案、权限使用说明 | P1（上架前必须） |
| 3 | 通知权限申请时机目前是"用户主动进设置页才请求"——合规上安全，产品上应改为"上下文时机主动请求" | P1 |
| 4 | 有利条件应保留并写进隐私政策：不含 Google 服务、无 SDK 上报、无账号——合规成本天然低 | — |

### 1.7 商业化路径（可选，不强推）

不建议做的：

- **不建议接广告 SDK**：与"黑白极简、无追踪、无 Google 服务"的产品人设直接冲突，且广告 SDK 是国内商店合规审查的重灾区。
- **不建议现阶段做付费订阅**：42 篇存量、单人维护，付费承诺兑现不了就是口碑事故。

值得考虑的方向（阶段三再议）：文章内原文出处赞赏位、站长精选集的"赞赏码"入口（静态按钮即可，零合规负担）。前提都是内容供给先跑起来。

### 1.8 产品打磨细节

| # | 问题 | 严重度 | 依据 |
|---|------|--------|------|
| 1 | **收藏/历史入口重复三套**：favorites 内部有"阅读历史" segment，profile 里又有独立"阅读历史"项指向独立路由，两处 UI 几乎相同——信息架构冗余 | P1 | `(tabs)/favorites.tsx` vs `history.tsx` |
| 2 | 分享卡片封面占位色硬编码浅灰，深色模式下封面加载时会闪一块亮灰 | P2 | `article/[id].tsx` |
| 3 | 无障碍只有 `accessibilityLabel`，无 `accessibilityRole="button"`；收藏 toggle 无状态播报 | P2 |
| 4 | 字号五档是固定 px，不随系统字体缩放——对老年用户不友好，阅读器类 App 这是基础预期 | P2 | `types.ts` FONT_SIZES |
| 5 | 无任何崩溃/错误上报（与"无追踪"一致，是取舍不是 bug），但也意味着没有任何用户反馈渠道：无反馈入口、无联系邮箱 | P1 | 全仓库 |
| 6 | 首屏每次渲染重复调 `listArticles()` 取总数，习惯问题 | P2 | `(tabs)/index.tsx` |
| 7 | 搜索只覆盖标题/作者/摘要/关键词，不搜正文——对"口袋资料库"定位，正文全文检索是高价值且 SQLite FTS 完全可本地实现 | P1 | `db.ts listArticles` |

## 二、改造路线图

### 阶段一「可用性补全」（1-2 个版本，目标：第一批外部用户能用起来、不丢数据、找得到入口）

| 工作项 | 验收标准 |
|---|---|
| 首次启动价值引导（3 屏轻量 onboarding） | 新装用户首次进入必见引导；可跳过；跳过后不再出现 |
| 本地数据导出/导入 | 收藏+历史+推荐列表可导出为 JSON；换机后导入可完整还原；损坏文件导入不崩 |
| 应用内更新检查 | 有新 release 时提示并可跳转下载页；无网络时静默失败 |
| 阅读进度记忆 | 长文读到一半退出，重开回到上次位置；首页出现"继续阅读"入口 |
| 去内部化文案 + 隐私政策页 | 全仓库搜不出"大肥鱼"等内部称呼；隐私政策完整可访问 |
| 通知权限上下文申请 | 用户读完第 3 篇文章时出现一次引导；拒绝后可在设置页重试 |
| 反馈渠道 | 我的页有"反馈问题"入口，mailto 或站点表单 |

### 阶段二「留存与增长」（目标：有节奏的内容 + 分发通道打开）

| 工作项 | 验收标准 |
|---|---|
| 内容节奏承诺机制（"每周三更新"写进 onboarding 与通知文案；weekly digest 页面） | 用户能预期更新时间；周更页面展示上周新增 |
| Web 落地页修复 | 未装 App 的用户点 `/article/<id>` 链接看到完整文章（站点端静态渲染） |
| 软著申请 + 商店上架（酷安优先，App 备案同步办） | 至少一个商店可搜索安装；材料齐全 |
| 分享链路优化 | 分享卡片入口提升到显著位置；分享文案带一句话定位 |
| SQLite FTS 全文搜索 | 搜正文关键词能命中文章并高亮片段 |
| 信息架构收敛 | 收藏/历史入口归一为一份实现 |

### 阶段三「规模化」（目标：内容生产可持续、数据可迁移、可尝试变现）

| 工作项 | 说明 |
|---|---|
| 内容生产工具链 | 半自动抓取 + LLM 辅助结构化草稿 + 站长审核发布，把单篇录入成本降一个数量级。这是整个产品最大的杠杆 |
| 轻量同步服务（可选） | 若用户量证明值得，再上最小后端：匿名设备 ID + 收藏云备份。仍不做社交、不做评论 |
| 商业化试点 | 赞赏入口/精选集付费 |
| iOS 版评估 | 仅当安卓端留存数据成立后再议 |

## 三、第一阶段可实施改造清单（当前代码库内，无后端，按优先级）

### 1. 阅读进度记忆 + 继续阅读（P0）

**为什么排第一**：这是"口袋阅读器"定位下最伤核心体验的缺失，且完全本地实现，复用现有 `user_state` 表模式。

**实现**：`src/lib/db.ts` 新增 `setProgress(id, scrollY, totalHeight)` / `getProgress(id)`；`article/[id].tsx` 的 `onScroll` 节流存储（每 2 秒或每 5% 进度），加载完成后 `scrollRef.scrollTo` 恢复；进度 >90% 时清除。首页 `(tabs)/index.tsx` 顶部在有未读完文章时渲染一张"继续阅读：标题"卡片。

**验收**：读一篇长文至 40% 处退出杀进程，重开回到 40%；读完的文章不再出现在继续阅读卡片；首页卡片点击直达位置。

### 2. 本地数据导出/导入（P0）

**实现**：`src/lib/db.ts` 已有全部读取函数，新增 `exportUserData()` 聚合成 JSON（含 schema_version），通过 `expo-sharing` 分享出去；导入用 `expo-document-picker` 选文件，按 schema 校验后逐条 upsert（收藏按文章 id 去重）。入口放 `(tabs)/profile.tsx`，命名"备份与恢复"。

**验收**：导出 → 清除应用数据重装 → 导入，收藏/历史/推荐列表/已读标记全部还原；导入损坏文件时给出明确错误且不污染现有数据。

### 3. 首次启动价值引导（P0）

**实现**：新增路由 `src/app/onboarding.tsx`，首次启动时 redirect 过去。3 屏即可：① 离线全文（"装好即读，断网也能读"）；② 人工精选（"每篇都由站长读过才收录"——这是与算法推荐流的差异化）；③ 通知引导（顺手在这里放权限请求按钮）。跳过/完成标记写 AsyncStorage。黑白风格直接用现有 theme token。

**验收**：新装首启必见、可跳过、跳过后永不再现；升级安装的老用户不看到。

### 4. 去内部化文案 + 隐私政策页（P0，合规前置）

**实现**：全局搜索替换内部称呼（`recommend.tsx` 的"大肥鱼"→"站长"或"编辑"，复制文案改为"复制全部链接（N 条），发送给站长即可收录"）。新增 `src/app/privacy.tsx` 本地隐私政策页（数据全部存本机、不采集不上报、通知与相册权限用途声明），about 页加"隐私政策"入口。

**验收**：`grep -r "大肥鱼" src/` 零结果；隐私政策在 App 内和站点均可访问；权限声明覆盖通知、媒体库写入两项。

### 5. 应用内更新检查（P1）

**实现**：不改服务端——启动时（节流，每 24h 一次）请求 GitHub Releases API `repos/<owner>/<repo>/releases/latest`（公开接口，无鉴权），比对 `tag_name` 与 `Constants.expoConfig.version`。有新版本时在 `(tabs)/profile.tsx` 顶部与 `about.tsx` 显示"新版本 vX 可用"行，点击打开 release 页。网络失败静默。新增 `src/lib/updateCheck.ts`。

**验收**：发布新 tag 后 24h 内已装用户可见提示；断网/接口失败完全静默；版本相同时无任何 UI 变化。

### 6. 通知权限上下文申请（P1）

**实现**：不改通知逻辑，只改申请时机。在 `article/[id].tsx` 的 `markRead` 路径上计数，用户读完第 3 篇时在文章页底部展示一次非阻断引导条（"想在有新文章时收到提醒？"→ 触发 `requestNotificationPermission`）；拒绝后不再出现，设置页的引导逻辑保持不变。

**验收**：第 3 篇文章阅读中出现且仅出现一次；授权后后台同步自动注册；拒绝过不再骚扰。

### 7. 反馈入口（P1）

**实现**：`(tabs)/profile.tsx` rows 数组加一行"反馈问题"，`Linking.openURL('mailto:...')`，预填版本号方便排查。

**验收**：点击唤起邮件客户端，正文预填 App 版本。

### 8. 深色模式与无障碍细节修复包（P2，顺手做）

**实现**：① `article/[id].tsx` 封面占位色 `#E4E4E7` 改为 `theme.surface`；② 全部图标 `Pressable` 补 `accessibilityRole="button"`，收藏按钮 label 动态为"已收藏/未收藏"；③ 字号五档乘以系统 `getFontScale()` 封顶 1.3。

**验收**：深色模式封面加载无亮块闪现；TalkBack 可正确朗读按钮类型与收藏状态。

## 四、明确不建议做的事（以及理由）

1. **不建议现阶段做账号体系**：无后端硬约束；用户量级不值得；"无账号·无追踪"是当前人设。用导出/导入兜底即可。
2. **不建议做 App 内自动转换推荐链接**：这是服务端抓取+转换能力，静态托管做不了；现有"复制给站长"流程虽原始但诚实。
3. **不建议接任何统计/崩溃 SDK**：与隐私政策承诺冲突；单人维护用 mailto 反馈 + GitHub issue 足够。
4. **不建议在阶段一重构信息架构（合并 favorites/history）**：有价值但不是外部用户痛点，且改动会碰三个页面；放阶段二。
5. **不建议做"每日推荐"类高频召回承诺**：内容供给是单人手工，承诺高频兑现不了比不承诺伤害更大。承诺"每周"，宁低勿高。
6. **不建议急着上架全量国内商店**：先酷安（审核宽松、目标人群匹配）验证分发，再投入华为/小米的材料与合规成本；软著流程则要立即启动因为它挡所有商店。

---

**核心结论**：当前代码库的工程底座（离线同步、签名发布、App Links）已经超出典型 demo 水平，阶段一不需要写任何服务端，8 项改造全部落在现有文件体系内，预计 2-3 周单人可完成。做完这批，产品才第一次具备"给陌生人用"的资格；之后真正决定生死的是站长的内容供给节奏。
